# 쉼터 봉사 1365 활동일지 자동화 PRD

2026년 11월 10일 

## 1. 개요

봉사자가 쉼터 현장에서 폼을 제출하면, 매주 화요일 오전에 지난주(월~일) 활동일지 PDF가 자동으로 만들어지고 운영진이 텔레그램에서 확인하면 자원봉사센터로 메일이 발송된다.

**배경**

- 쉼터 봉사자가 1365 봉사시간을 인정받으려면 「자원봉사자 활동 일지」 양식을 채워 ㅇㅇ구자원봉사센터에 제출해야 한다.
- 지금은 정보를 수기로 모아 양식을 채우고 있어 운영진 부담이 크다.
- 구글 폼은 위치 확인이 안 돼서, 현장에서만 제출 가능한 자체 HTML 폼이 필요하다.

**목표**

- 봉사자는 현장에서 QR로 접속해 1분 안에 제출한다.
- 운영진은 텔레그램 버튼과 자연어 대화만으로 확인, 수정, 발송을 끝낸다.
- 개인정보는 발송 후 3개월이 지나면 자동 파기한다.
- 운영 비용 0원 (구글 무료 서비스 + 정적 호스팅 + 무료 LLM 티어)

**범위 밖**

- 1365 포털 직접 입력
- 쉼터 사진 업로드와 얼굴 블러 처리 (별도 과제)

## 2. 시스템 구조

서버 없이 Apps Script 웹앱 하나가 백엔드를 맡는다. 폼만 정적 페이지로 외부에 두는데, Apps Script 자체 HTML은 iframe 안에서 돌아 위치 권한이 막힐 수 있기 때문이다.

[embed: node/d284617a-5e26]

폼 제출과 텔레그램 웹훅은 같은 웹앱 URL로 들어오고, 시트·드라이브·Gmail은 쉼터 공용 계정 권한으로 접근한다. 비용은 구글 무료 할당량과 정적 호스팅, LLM 무료 티어 안에서 0원이다.

## 3. 사용자 흐름

봉사자는 현장에서 제출만 하고, 나머지는 매주 화요일 운영진이 텔레그램에서 버튼 두 번으로 끝낸다.

[embed: node/2a8cb314-eaa0]

수정은 ① 마감 알림 이후부터 메일 발송 전까지 언제든 받고, 반영되면 PDF를 다시 만들어 ②부터 이어간다. 작성과 발송은 되돌릴 수 없으므로 자연어가 아닌 버튼으로만 승인한다.

## 4. 기능 요구사항

### 4.1 봉사자 입력 폼 (정적 HTML)

- 입력 항목: 이름, 생년월일(yy.mm.dd), 연락처, 활동시간, 개인정보 제공 동의(체크박스, 필수), 전자서명(필수)
  - 전자서명: 손가락으로 그리는 서명판(canvas). [지우기] 가능, 서명하지 않으면 제출 불가. PNG로 줄여서 함께 전송하고, 확인 팝업에도 서명 이미지를 보여준다.
  - 활동시간 선택 방식은 설정값 `TIME_MODE`로 고른다. 서버에서도 같은 규칙으로 다시 검증한다.
    - `free`: 시작·종료 시각을 10분 단위로 고른다. 선택 범위는 `ACTIVITY_WINDOW`, 총합은 `MAX_ACTIVITY_HOURS`(기본 8시간) 이하.
    - `preset`: 오전·오후·종일 중 하나를 고른다. 각 시간은 `TIME_MORNING`, `TIME_AFTERNOON`, `TIME_FULLDAY`에서 읽고, 폼은 선택지 키만 보낸다.
  - [제출하기]를 누르면 바로 보내지 않고 확인 팝업을 띄운다: 이름, 생년월일, 연락처, 활동시간 `HH:mm~HH:mm (총 n시간)`, 개인정보 제공 동의 + "위 내용으로 제출하시겠습니까? 제출 후에는 수정할 수 없습니다."
  - 생년월일, 연락처는 입력 형식 검증 (예: `95.03.12`, `010-1234-5678`)
- 봉사일자는 사용자가 고르지 않는다. 서버가 제출 시점의 한국 날짜로 자동 입력한다.
- 접속 시 브라우저 Geolocation API로 위치 권한을 요청한다.
  - 권한 거부, 위치 획득 실패 시 제출 버튼 비활성화 + "쉼터에서 접속해 주세요" 안내
- 동의 문구: 양식 하단의 1365 실적등록 목적 개인정보 제공 동의 문구를 그대로 노출한다.
- 제출 성공 시 완료 화면, 실패 시 사유 표시 (위치 범위 밖, 중복 제출, 서버 오류)
- 호스팅: Vercel 또는 GitHub Pages. 데이터는 Apps Script 웹앱 URL로 POST한다 (`Content-Type: text/plain`, CORS preflight 회피).

### 4.2 제출 처리 (Apps Script `doPost`)

- 서버에서 쉼터 좌표(`SHELTER_LAT`, `SHELTER_LNG`)와의 거리를 하버사인 공식으로 계산, `GEOFENCE_RADIUS_M`(기본 300m) 밖이면 거부한다.
- 중복 키 = 봉사일자 + 이름 + 생년월일. 이미 있으면 거부한다.
- 서명 이미지는 PNG 형식·크기(300KB 이하)를 확인한 뒤 드라이브 서명 폴더(`SIGNATURE_FOLDER_ID`)에 저장한다. 파일명은 `봉사일자_UUID.png`로 개인정보를 넣지 않는다.
- 신청 탭에 한 행 추가, 진행상태 = `접수`, 작성일시 자동 기록, 서명 파일 ID 기록 (행 추가 실패 시 서명 파일은 휴지통으로)
- 거리값(m)도 함께 저장해 운영진 참고용으로 쓴다.

### 4.3 주간 활동일지 생성

- 매주 화요일 오전 9~10시 트리거가 지난주 월~일 `접수` 건을 모아 마감 알림을 보낸다.
- 운영진이 작성을 승인하면 PDF를 만든다.
  - 구글 시트 템플릿(양식 복제본)에 값을 채운 뒤 PDF로 내보낸다.
  - 한 장에 11명, 초과 시 여러 장. 봉사일자 → 작성일시 순 정렬
  - 고정값: 활동기관, 활동내용(공통), 기관명, 담당자, 연락처, 직인 이미지
  - 본인서명/정보제공 동의 칸: 봉사자가 제출한 서명 이미지
  - 하단 날짜: PDF 생성일
- 생성된 PDF는 드라이브 지정 폴더에 저장하고 텔레그램으로 전송한다.

### 4.4 텔레그램 봇 (운영진 그룹)

- 운영진 그룹 채팅에 봇을 초대해 쓴다. 허용된 사용자 ID(`ADMIN_USER_IDS`)만 버튼과 명령을 처리한다.
- 버튼을 누르면 메시지를 수정해 처리자를 남긴다 (예: "✅ 작성 승인 (by 홍길동)").
- 처리한 `update_id`를 기억해(CacheService, 6시간) 텔레그램 재전송으로 인한 중복 처리를 막는다. 버튼 처리는 처리로그에 `update_id`와 함께 남긴다. (그룹의 모든 메시지를 시트에 쓰지 않기 위해)
- 웹훅 응답은 200(HtmlService)으로 돌려준다. ContentService 응답은 302 리다이렉트가 되어 텔레그램이 오류로 보고 재전송할 수 있다.
- `/myid`: 누구나 보낼 수 있고, 봇이 보낸 사람의 user ID를 답한다 (운영진 등록용).
- 이미 처리된 단계의 버튼을 다시 누르면 "이미 처리된 요청이에요"로 응답한다.

### 4.5 자연어 수정

- 운영진이 자유 문장으로 수정을 요청한다. 예: "3번 연락처 010-1111-2222로 바꿔줘", "김민지 11/4 10:00~14:00로 추가해줘", "5번 삭제"
- LLM이 요청을 구조화된 명령으로 변환한다: `{action: update|add|delete, target_no, field, value}`
- 적용 전 반드시 확인 메시지 + [확인] [취소] 버튼. 확인 시에만 시트에 반영한다.
- 동명이인, 대상 불명확, 형식 오류는 되묻는다.
- PDF 생성 후 · 메일 발송 전에 수정되면 PDF를 다시 만들어 전송한다.
- LLM에는 해당 주차 명단 중 요청 해석에 필요한 최소 정보만 보낸다.
- 운영진이 입력한 문장에 포함된 연락처·생년월일은 LLM 전송 전에 코드가 정규식으로 찾아 `<PHONE_1>`, `<BIRTH_1>` 같은 자리표시자로 치환한다. LLM 응답의 `value`에 들어온 자리표시자는 코드가 원래 값으로 되돌려 확인 메시지와 시트 반영에 쓴다. 따라서 LLM은 연락처·생년월일의 실제 값을 보지 못한다.
- 무료 티어(Gemini Flash)는 입력이 서비스 개선에 사용될 수 있으므로, 개인정보가 LLM에 넘어가지 않도록 위 마스킹을 필수로 한다. 마스킹이 안 되는 이름은 요청 해석에 필요한 행에 한해 전달한다.
- 작성/발송 같은 단계 승인은 자연어 대신 버튼으로 받는다 (되돌릴 수 없는 동작 보호).

### 4.6 메일 발송

- 쉼터 공용 Gmail 계정에서 `MAIL_TO`로 발송, 참조 `MAIL_CC`
- 제목·본문·첨부파일명은 설정값 템플릿 사용. 치환 변수: `{start}`, `{end}`, `{count}`, `{sent_date}`
- 최신 PDF 첨부 필수. 첨부가 없으면 발송하지 않고 오류 알림
- 발송 성공 시 신청 행 진행상태 = `발송완료`, 주차 탭에 발송일시·처리자 기록
- 같은 주차는 한 번만 발송 (주차 상태로 중복 방지)

### 4.7 개인정보 파기

- 매월 1일 실행: 발송일로부터 3개월이 지난 주차의 신청 행과 드라이브 PDF, 서명 이미지를 삭제한다.
- 메일(보낸편지함)은 파기 대상에서 제외한다.
- 실행 전날 텔레그램으로 파기 예정 알림 (대상 주차, 건수)
- 파기 후 주차 탭 상태 = `파기완료` (행 자체는 기록용으로 남기고 개인정보 없음)

## 5. 데이터 구조

구글 시트 하나에 탭 4개를 둔다. 시트와 드라이브 폴더는 쉼터 공용 Gmail 계정 소유, 운영진 계정에만 공유한다.

**신청 탭** (봉사자 1명 1행)

| 컬럼         | 형식                | 비고                              |
| ------------ | ------------------- | --------------------------------- |
| 봉사일자     | yyyy-MM-dd          | 서버가 제출일로 자동 입력         |
| 이름         | 텍스트              |                                   |
| 생년월일     | yy.mm.dd            | 텍스트 서식 (자동 날짜 변환 방지) |
| 연락처       | 010-0000-0000       | 텍스트 서식                       |
| 활동시간     | 10:00~14:00         | 시작~종료 시각 (10분 단위)        |
| 정보제공동의 | Y                   | 미동의는 제출 불가                |
| 진행상태     | 접수 / 발송완료     |                                   |
| 작성일시     | yyyy-MM-dd HH:mm:ss | 자동 수집                         |
| 거리(m)      | 숫자                | 쉼터와의 거리, 참고용             |
| 주차ID       | 2026-W46            | 생성 시 채움                      |
| 서명파일ID   | 드라이브 파일 ID    | 서명 폴더의 PNG                   |

**주차 탭** (주 1회 1행)

| 컬럼                      | 비고                       |
| ------------------------- | -------------------------- |
| 주차ID                    | ISO 주차, 예: 2026-W46     |
| 시작일 / 종료일           | 월요일 / 일요일            |
| 상태                      | 아래 상태값                |
| 신청자수                  |                            |
| PDF 파일 ID               | 재생성 시 최신 값으로 교체 |
| 작성 승인자 / 발송 처리자 | 텔레그램 이름              |
| 발송일시                  |                            |
| 파기일시                  |                            |

**대화상태 탭**: 자연어 수정의 확인 대기 건 저장 (요청 ID, 주차ID, 변환된 명령 JSON, 요청자, 생성시각)

**처리로그 탭**: 버튼 처리 기록(`update_id`, 처리자), 수정 이력(누가, 어떤 컬럼의 값을 바꿨는지만 기록. 이전값·새값은 어떤 필드든 남기지 않는다, 9장), 오류 기록

**주차 상태값**

1. `마감대기`: 화요일 트리거가 마감 알림을 보낸 상태
2. `작성완료`: PDF 생성 + 확인 요청 전송
3. `발송대기`: 발송 여부 질문 전송
4. `발송완료`: 메일 발송 성공
5. `파기완료`: 개인정보 삭제 완료

수정이 들어오면 `작성완료` 이전 단계로 돌아가 PDF를 다시 만든다. `발송완료` 이후에는 수정 요청을 받지 않고 안내만 한다.

## 6. 텔레그램 메시지 양식

모든 단계 메시지에는 번호 붙인 명단을 함께 보내 수정 요청 시 번호로 지칭할 수 있게 한다. 날짜 표기는 `26년 11월 10일 화`.

**① 마감 알림** (화요일 09~10시)

```
26년 11월 3일 월 ~ 11월 9일 일 / 1365 봉사시간 신청자: 7명

1. 11/3 월 홍길동 95.03.12 010-1234-5678 10:00~14:00
2. 11/3 월 김민지 01.07.21 010-2222-3333 14:00~18:00
...

활동일지를 작성할까요? 수정할 내용이 있으면 메시지로 알려주세요.
```

버튼: [작성하기]

**② 작성 완료** (PDF 첨부)

```
활동일지를 작성했습니다. 확인 부탁드립니다. (총 7명, 1장)
```

**③ 발송 확인** (②에 이어서)

```
활동일지를 담당자(manager@example.com)에게 전송할까요?
```

버튼: [전송하기]

**④ 발송 완료**

```
메일을 발송했습니다. (by 홍길동, 26년 11월 10일 화 10:24)
```

**수정 확인** (자연어 요청 후)

```
아래와 같이 수정할까요?
3번 홍길동 연락처: 010-1234-5678 → 010-1111-2222
```

버튼: [확인] [취소] → 확인 시 "수정했습니다. 활동일지를 다시 작성할게요." 후 ② 재전송

**재알림** (화요일 18~19시, 그날 발송 완료 전이면)

```
[재알림] 26년 11월 3일 월 ~ 11월 9일 일 활동일지가 아직 발송되지 않았어요. (현재 단계: 발송대기)
```

현재 단계의 버튼을 다시 붙인다.

**파기 예정 알림** (매월 말일 09~10시)

```
내일(12월 1일) 개인정보 파기가 진행됩니다.
대상: 2026-W33 ~ 2026-W36 (4주차, 총 26명)
```

**오류 알림**

```
⚠️ [오류] 메일 발송 실패: <에러 메시지 요약>
주차: 2026-W45 / 다시 시도하려면 [전송하기]를 눌러주세요.
```

## 7. 트리거 스케줄

Apps Script 시간 기반 트리거는 1시간 범위로 실행된다. 스크립트 시간대는 `Asia/Seoul`로 설정한다.

| 트리거           | 주기        | 실행 시간대 | 동작                                                   |
| ---------------- | ----------- | ----------- | ------------------------------------------------------ |
| `weeklyClose`    | 매주 화요일 | 09~10시     | 지난주 월~일 `접수` 건 집계, 주차 행 생성, ① 마감 알림 |
| `weeklyReminder` | 매주 화요일 | 18~19시     | 해당 주차가 `발송완료` 전이면 재알림                   |
| `purgeNotice`    | 매일        | 09~10시     | 내일이 1일이면 파기 예정 알림, 아니면 종료             |
| `monthlyPurge`   | 매월 1일    | 09~10시     | 발송 후 3개월 지난 주차의 신청 행·PDF 삭제             |

텔레그램 웹훅(`doPost`)과 폼 제출(`doPost`)은 같은 웹앱 URL로 들어오므로, 요청 본문 형태(`update_id` 유무)로 구분한다.

폼은 활동시간 선택 방식과 범위(`TIME_MODE` 등)를 Apps Script `doGet`으로 내려받으므로 폼 HTML은 수정 없이 유지된다.

## 9. 예외 처리와 보안

**예외 처리**

| 상황                      | 처리                                                         |
| ------------------------- | ------------------------------------------------------------ |
| 위치 권한 거부 / 반경 밖  | 제출 차단, 안내 문구                                         |
| 중복 제출                 | 차단, "오늘 이미 제출하셨어요"                               |
| 지난주 신청자 0명         | "지난주 신청자가 없습니다" 한 줄 알림, 주차 행은 `발송완료` 없이 종료 |
| PDF 생성 실패             | 오류 알림 + [다시 작성] 버튼                                 |
| 메일 발송 실패            | 오류 알림 + [전송하기] 버튼 유지, 상태 변경 없음             |
| LLM 호출 실패 / 해석 불가 | "요청을 이해하지 못했어요. 예: 3번 연락처 010-… 로 바꿔줘"   |
| 발송완료 후 수정 요청     | 수정 불가 안내 (정정은 수동 처리)                            |
| 허용되지 않은 사용자      | 버튼 응답 "권한이 없어요", 메시지는 무시                     |
| 텔레그램 중복 수신        | `update_id` 캐시로 무시                                      |
| 동시 버튼 클릭            | `LockService`로 주차 단위 잠금, 이미 처리된 단계면 안내      |

**보안·개인정보**

- 시트·드라이브는 공용 계정 소유, 운영진 계정만 공유 (링크 공유 금지)
- 텔레그램 웹훅 검증: Apps Script 웹앱은 요청 헤더(`X-Telegram-Bot-Api-Secret-Token`)를 읽을 수 없으므로, 웹훅 URL 쿼리 파라미터에 비밀값(`WEBHOOK_SECRET`)을 붙여 등록하고 `doPost`에서 비교한다.
- 폼 제출 요청에는 위치 검증 외 인증이 없으므로, 같은 연락처로 짧은 시간 다수 제출 시 차단한다 (간단한 레이트 리밋).
- LLM에 보내는 데이터는 해당 주차 명단의 번호·이름·수정 대상 필드로 최소화한다.
- 운영진 메시지 속 연락처·생년월일은 LLM 전송 전에 자리표시자로 치환하고, 응답을 받은 뒤 코드에서 복원한다 (4.5장).
- 로그에는 연락처·생년월일을 남기지 않는다 (번호와 이름만).

**레포 구조 (제안)**

```
shelter-volunteer/

│   ├── index.html
│   ├── app.js           # 위치 확인, 검증, POST
│   └── style.css

│   ├── Main.js          # doGet / doPost 라우팅
│   ├── Form.js          # 제출 처리, 지오펜스, 중복 체크
│   ├── Sheet.js         # 시트 접근 헬퍼
│   ├── Pdf.js           # 템플릿 채우기 → PDF
│   ├── Telegram.js      # 메시지·버튼·콜백
│   ├── Nlu.js           # LLM 자연어 → 명령
│   ├── Mail.js          # 메일 발송
│   ├── Triggers.js      # 주간·재알림·파기
│   └── Config.js        # Script Properties 읽기
└── README.md            # 초기 설정 절차
```

**구현 단계**

1. 시트 탭·컬럼 생성 스크립트 + `Config.js` (설정값 누락 시 오류 알림)
2. 폼 HTML + `doPost` 제출 처리 (지오펜스, 중복 체크) → 폰으로 현장 테스트
3. 텔레그램 봇 연결: 웹훅 등록 함수, 메시지 전송, 버튼 콜백, 권한·중복 체크
4. PDF 생성: 양식 템플릿 시트 제작 → 값 채우기 → 11명 단위 페이지 분할 → PDF 내보내기 (기간 지정 수동 실행으로 먼저 검증)
5. `weeklyClose` 트리거 + ① 마감 알림 + [작성하기] → 4단계 PDF 생성 연결
6. 메일 발송 + 상태 전이 + 중복 발송 방지
7. 자연어 수정: LLM 프롬프트(JSON 출력 강제) → 확인 버튼 → 반영 → PDF 재생성
8. 재알림, 파기 알림, 파기 배치
9. 엔드투엔드 테스트: 테스트용 텔레그램 그룹 + 테스트 수신 메일로 한 주기 전체 실행, 이후 실제 값·현장 확인·QR 부착으로 운영 시작

**Claude Code에 줄 때 메모**

- 이 문서를 레포에 `docs/PRD.md`로 넣고 "단계별로 구현, 각 단계 끝에 수동 테스트 방법 알려줘"로 시작한다.
- Apps Script 로컬 개발은 `clasp`(`npm i -g @google/clasp`)로 push/pull 한다.
- 시간 트리거와 웹훅은 코드로 등록하는 `setupTriggers()`, `setWebhook()` 함수를 만들어 한 번 수동 실행한다.
- 테스트 중에는 `MAIL_TO`를 본인 메일로 바꿔 실제 센터로 나가지 않게 한다.
